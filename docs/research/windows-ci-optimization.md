# Оптимизация Windows CI Minotaur (2026-10-29)

## Решение: оптимизацию отложить

По решению пользователя от 2026-10-29 действующий Windows CI оставлен без изменений.
Исторический `-j4` штатный, подтверждённые сборки стабильны, CPU при компиляции почти полностью
загружен. Доказательств существенного ускорения при большем параллелизме нет.
Вернуться к оптимизации только если время сборки станет реальной проблемой или появятся
объективные данные о возможном существенном ускорении.

Исследование выполнено в `feature/minotaur-rebalance`, HEAD `d8e5fe5`.
Подготовленные, но не отправленные изменения workflow, монитора и его тестов отменены.
Параметр `build_jobs` и новые Step Summary не внедрены. Существующие мониторинг,
защита памяти и автоматический выбор параллелизма сохранены.
Игровой код, ресурсы, формат ZIP, состав патча, коммиты, upstream/main и Ubuntu safe-heavy-run
не изменены. Новые CI-сборки, push и публикация не выполнялись.

## История и действующие ограничения

Первый `.github/workflows/minotaur-windows.yml` (`4c3d726`) уже использовал `--parallel 4`.
`c991da3` заменил константу эвристикой `min(8, cpu_count, floor((available_RAM - 2 GiB) / 2 GiB))`.
На runner 4 vCPU результат — 4. В истории этого workflow, включая доступные локальные refs,
`-j25`/`--parallel 25` не найден. Это не доказательство отсутствия внешних ручных запусков.
В CMake проекта дополнительных JOB_POOL-ограничений не найдено. Независимый upstream workflow
`packages.yml` имеет свои настройки параллелизма; они не управляют Minotaur workflow.

Действующий workflow вызывает monitor с `--probe`, который выбирает параллелизм по указанной
эвристике; ручного `build_jobs` в нём нет.
Защита по физической/commit-памяти сохранена: отказ перед запуском при pressure;
при свободной RAM ниже max(512 MiB, 8% total) или commit headroom ниже 256 MiB
в течение 10 секунд — `taskkill /T /F`, exit 137. Это реактивная защита, не гарантия отсутствия OOM
при резком скачке памяти. Параллелизм автоматически не понижается, неудачная сборка не повторяется.
Job timeout остаётся 240 минут; concurrency отменяет предыдущий run той же ветки.
Ubuntu VM имеет отдельные правила и не используется для Windows-экспериментов.

## Возможные направления при возобновлении исследования

1. Checkout (5:43): проверить объём скачивания и checkout/LFS по логу; сузить sparse paths лишь
   после проверки обращений packager. Уже используются depth=1 и sparse checkout.
   Простое дальнейшее сокращение допустимо только с прежним manifest/составом пакета.
2. Configure (2:35): рассмотреть cache исходных архивов зависимостей, ключ по их точным версиям.
   Не переносить целиком build tree с другого SHA. Cache должен допускать полностью холодную сборку.
3. MSYS2 (1:34): сначала проверить попадания штатного cache setup-msys2; отключение `update: true`
   меняет версии окружения и не является эквивалентной оптимизацией без отдельной фиксации toolchain.
4. Программа + tests (35:15): возможное сравнение с -j8 требует отдельного согласования. Unit compile уже использует CPU почти полностью.
   Позже можно исследовать повторную компиляцию shared sources и compiler cache, но это отдельная работа.
5. Контент (2:06): потенциально полезен cache детерминированных результатов cooker с ключом по
   source assets, cooker и настройкам. Нельзя просто пропустить подготовку: она нужна для индекса
   и корректного сравнения пакетов. Сначала проверять совпадение content IDs и payload manifest.
6. Сами тесты и ZIP занимают секунды: их сокращение почти ничего не даст.

Кэши и исключения файлов не внедрялись; перечисленные идеи не являются доказанным ускорением.
Главные подтверждённые накладные расходы — checkout и configure; ускорение ZIP не приоритет.

Это исходная база, а не завершённый A/B-эксперимент. Запуски -j8/12/16/25 не выполнялись
и не планируются в рамках текущего решения. Прежние инструкции с `build_jobs` неприменимы:
этого параметра в действующем workflow нет.

Если исследование будет возобновлено по указанным выше основаниям, сначала отдельно согласовать
изменения и эксперимент. Сравнивать -j4 и -j8 последовательно на одинаковом SHA, с одинаковыми
runner image, vCPU/RAM, версиями toolchain, baseline, режимом пакета и состоянием cache.
Оценивать время всего успешного job, времена program/unit-build, результаты тестов и запас
RAM/commit. Пиковая загрузка CPU и свободная RAM сами по себе не доказывают возможность ускорения.
Более высокий параллелизм рассматривать только при подтверждённой перспективе выигрыша.
