# Minotaur Windows CI: как проверять изменения до долгой сборки (2026-11-14)

Решение 2026-10-29 ([windows-ci-optimization.md](windows-ci-optimization.md)) откладывало оптимизацию, «пока время
сборки не станет реальной проблемой». Перенос на полную 2.3 потребовал пяти Windows-сборок по 60–90 минут, каждая
из которых находила одну ошибку. Пользователь попросил перейти к приёмам, которые ловят такие ошибки заранее, и
взять за образец оригинальный OpenYAMM.

## Что делает upstream (`.github/workflows/packages.yml`)

- Ресурсы упаковываются **один раз на Linux** отдельной задачей `content`. Там собирается только маленький cooker.
- Программа для Windows **кросс-компилируется на Linux** (MinGW), тонкая и без тестов; модульные тесты идут на Linux.
- Задача `checks` на каждой ОС скачивает готовые программу и ресурсы и только играет штатные сценарии
  (`tests/scenarios/release/scenarios.txt`) с `--asset-root`.
- Всё параллельно; индекс ресурсов присоединяется к программе позже (`packaging/publish_release.py assemble`).

## Что принято для Minotaur (`.github/workflows/minotaur-windows.yml`)

Сборка программы остаётся нативной MSYS2 на Windows: на ней работают тесты Minotaur, Медузы, импортёра и
установщика PowerShell, и переход на кросс-компиляцию — отдельное решение. Остальное повторяет upstream:

| Задача | Где | Что | Время |
|---|---|---|---|
| `preflight` | Linux | `tools/check_minotaur_workflow.py`, тесты Python-инструментов, база и версия | 1–2 мин |
| `update_tests` | Windows | установщик PowerShell 5.1, инструменты на Windows-Python | ~3 мин |
| `content` | Linux | полная упаковка (MM6–MM9, языки, Медуза), `--content-only` проверка | параллельно |
| `windows` | Windows | программа и тесты через ccache, тонкая программа, затем все группы тестов | ~50 мин холодная, меньше с кэшем |
| `package` | Windows | программа + ресурсы (`tools/assemble_minotaur_package.py`), патч или новая база, полная установка, сценарии | |

- **ccache.** Кэш восстанавливается до компиляции и сохраняется даже при падении тестов. Повторная сборка без правок
  C++ компилирует почти ничего. Предкомпилированных заголовков в проекте нет, особых настроек не нужно.
- **Повторное использование.** `reuse_build_run` и `reuse_content_run` берут программу или ресурсы из прошлого
  запуска: правка упаковки или сценария проверяется без компиляции, правка программы — без упаковки.
- **Все ошибки за один запуск.** Тесты (`tools/minotaur_ci_tests.sh`) и сценарии идут до конца и перечисляют все
  падения; прежний workflow останавливался на первом шаге.
- **Пакеты выгружаются до проверок**, так что установщик доступен, даже если упал тест или сценарий.
- **Состав поставки не сужается.** Проверка workflow требует, чтобы `content` выкачивал всё, что выкачивает desktop-
  задача upstream, и каждый мир `packs.yml`, без `--world`/`--engine-only`; проверка ресурсов (`--content-only`)
  сверяет пакеты, языки и наборы правил.

## Перед каждым push (локально, на этой машине)

1. `python3 tools/check_minotaur_workflow.py` и тесты инструментов в `tools/` (`test_minotaur_updates.py`,
   `test_verify_minotaur_windows_package.py`, `test_assemble_minotaur_package.py`).
2. `tools/minotaur_ci_tests.sh build/tests <группы>` через `safe-heavy-run`: те же фильтры, что в CI. Группы `mm9` и
   `mm9-ai` и три случая `ScriptedMapRegressionTests` требуют полные данные карт, которых нет в разреженной рабочей
   копии; их результат здесь не показателен.
3. Для изменений C++ — тесты под AddressSanitizer: обращение к освобождённой памяти, которое на Linux проходит молча,
   а на Windows ломает тест, видно сразу. Каталог `build-asan`, конфигурация как у `build` плюс
   `-DCMAKE_BUILD_TYPE=RelWithDebInfo`, `-fsanitize=address -fno-omit-frame-pointer` в флагах C/C++ и компоновщика и
   `-DCMAKE_CXX_STANDARD_LIBRARIES=/lib/x86_64-linux-gnu/libxcb.so.1` (без оптимизации `-O3` статическая `libX11`
   sysroot втягивает `libxcb`). Запуск: `LD_LIBRARY_PATH` дополнить `build/sysroot/usr/lib/x86_64-linux-gnu`
   (`libOpenGL.so.0`), `ASAN_OPTIONS=detect_leaks=0`. Первая сборка модульных тестов — около 20 минут, дальше
   инкрементально. Проверено 2026-11-14: группы `medusa-importer`, `roguelike`, `updater` чисты, а возвращённая на
   время ошибка теста Медузы даёт `heap-use-after-free` со строкой освобождения и строкой обращения.
4. Новые сценарии — запуск движком: ключи проверяются до выполнения, даже без данных карты.

Полную упаковку локально не повторить: MM9 весит 3,4 ГБ, а GitHub отдаёт этой машине 20–70 КБ/с на соединение.

## Пять падений переноса и что их поймало бы

| Падение | Теперь ловит |
|---|---|
| Тест Чедиана без данных MM9 | `check_minotaur_workflow.py` (MM9 в checkout задачи `windows`), локальные группы |
| Висячий указатель в тесте Медузы | AddressSanitizer локально |
| Тесты регистра имён на NTFS | группа `medusa-importer` с исключениями, одна для CI и локально |
| Упаковщику нужен MM9 | `check_minotaur_workflow.py` |
| `iterdir`/`rglob` под Python MSYS2 | упаковка на Linux; инструменты проверяются на Windows-Python в `update_tests` за минуты |
